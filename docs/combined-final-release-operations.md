- **Restore rehearsal** uses an empty, isolated verified disposable matching Supabase PostgreSQL runtime. Suppress cron, outbound network and replayed queue delivery. ## Cutover and recovery sequence

1. Obtain explicit approval on exact source and release plan, privacy wording and activation boundaries. Identify operator and reviewer, affected tournament window, protected recovery target, final backup and an escalation contact. Check competition deadlines, paused/retriable jobs, active transactions, rule gates and dependencies. A visual maintenance page leaves existing clients and jobs able to write. Verify the actual write barrier before incompatible changes. Use a different window if affected writes cannot be isolated without risking legitimate matches or deadlines.
2. Keep the real mutation boundary paused through migration, canary and catch-up. Retain public reads and unaffected operations only where verified compatible. Use the exact feature-off candidate after the service-only Match Room transition. The old live deployment may resume writes only while the database remains on its old compatible boundary. Confirm competition-write rejections while paused, and keep a record of the time and cause of each stop.
3. Before resumption, verify public reads, live hotfix behavior, registered player and caster boundaries, authorised staff, results/brackets, exact-match assistance, legal and closed-account denial, notification and queue health, private objects, and normal pending actions. Resume existing production writes and scheduled jobs only after approved smoke and reconcile in-flight, deadline and queued items. Then activate Caster, Ready core, engagement and Wardrobe in separate approved steps. Check public crawler metadata after public activation using synthetic, non-sensitive evidence.
4. On failure, stop the affected stage. Keep compatible writes guarded. Turn off the affected feature and use the exact prepared recovery build, leaving durable Caster and competition data in place. For core authority failures, contain under the write barrier and repair forward using a newly reviewed migration or compatible app. Emergency database/Storage restore needs its own approval and data-loss decision. Reconcile all post-snapshot writes, closure records and confirmed erasures before reconnecting a restored system to public traffic. Do not use old code against new write authority or restore over live data as a routine rollback.
